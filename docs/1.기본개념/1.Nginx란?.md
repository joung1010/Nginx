## Nginx란?

**Nginx**(엔진엑스로 읽음)는 러시아의 개발자 Igor Sysoev가 2004년에 개발한 **오픈소스 웹 서버 소프트웨어**입니다. 원래는 러시아의 대형 포털 사이트 Rambler.ru의 높은 트래픽을 처리하기 위해 개발되었습니다.

### 🎯 Nginx의 핵심 철학

Nginx는 하나의 기능을 완벽하게 수행하자는 Unix 철학과는 다르게, **현실적인 웹 서비스 운영에 필요한 모든 기능을 통합**하여 제공하는 것을 목표로 합니다.

### 🔧 Nginx의 주요 기능들

nginx는 딱1가지 기능만을 가지고 있는 소프트웨어가 아니다. 다양한 기능들을 가지고 있다.

### 1. **웹 서버 (정적 컨텐츠 제공)**

정적 컨텐츠(HTML, CSS, JavaScript, 이미지 파일 등)를 클라이언트에게 직접 제공하는 기본적인 웹 서버 기능입니다. Nginx는 이 작업을 매우 효율적으로 처리하여 Apache 대비 **10배 이상 빠른 정적 파일 서빙 성능**을 보여줍니다.

**동작 방식:**

```
Client Request → Nginx → File System → Response
```

실제로 파일을 읽어서 네트워크로 전송할 때 **sendfile() 시스템 콜**을 사용해서 커널 레벨에서 직접 파일을 전송하므로 사용자 공간과 커널 공간 간의 데이터 복사 오버헤드가 없습니다.

```
server {
    listen 80;
    server_name example.com;
    
    location /images/ {
        root /var/www/html;
        expires 1y;                    *# 브라우저 캐시 1년 설정*
        add_header Cache-Control public;
    }
}
```

### 2. **리버스 프록시**

클라이언트의 요청을 받아서 백엔드 서버(WAS, API 서버 등)로 전달하고, 백엔드의 응답을 다시 클라이언트에게 중계해주는 역할입니다. 클라이언트 입장에서는 Nginx가 실제 서버인 것처럼 보이게 됩니다.

**활용 사례:**

- **내부망 보안**: 외부에서 직접 애플리케이션 서버에 접근할 수 없게 차단
- **포트 통합**: 외부에는 80/443 포트만 노출하고 내부적으로 8080, 9000 등 다양한 포트로 분산
- **Header 조작**: 클라이언트 IP, 호스트명 등의 정보를 백엔드에 전달

```
location /api/ {
    proxy_pass http://backend-server:8080;
    proxy_set_header Host $host;                    *# 원본 Host 헤더 전달*
    proxy_set_header X-Real-IP $remote_addr;       *# 클라이언트 실제 IP 전달*
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

### 3. **로드 밸런서**

여러 대의 백엔드 서버가 있을 때, 들어오는 요청을 각 서버에 적절히 분산시켜서 부하를 나누어 처리하도록 해줍니다. 특정 서버에 장애가 발생하면 자동으로 해당 서버를 제외하고 나머지 서버들로만 요청을 보냅니다.

**로드 밸런싱 알고리즘:**

- **Round Robin**: 순서대로 돌아가며 요청 분산 (기본값)
- **Least Connections**: 현재 연결 수가 가장 적은 서버로 요청 전달
- **Weight**: 서버별로 가중치를 설정하여 성능에 따라 요청 분배
- **IP Hash**: 클라이언트 IP를 해시하여 항상 동일한 서버로 요청 (세션 유지)

```
location /api/ {
    proxy_pass http://backend-server:8080;
    proxy_set_header Host $host;                    *# 원본 Host 헤더 전달*
    proxy_set_header X-Real-IP $remote_addr;       *# 클라이언트 실제 IP 전달*
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

### 4. **SSL/TLS 터미네이션 (SSL 가속기)**

HTTPS로 들어온 암호화된 요청을 Nginx에서 복호화한 후, 내부 백엔드 서버와는 일반 HTTP로 통신하도록 해주는 기능입니다. 이를 통해 **SSL 처리 부담을 백엔드 서버에서 Nginx로 이전**시킬 수 있습니다.

**장점:**

- **성능 향상**: 백엔드 서버들은 SSL 암복호화 작업을 하지 않아도 됨
- **인증서 관리 단순화**: Nginx에서만 SSL 인증서를 관리하면 됨
- **하드웨어 가속**: Nginx는 SSL 전용 하드웨어를 활용할 수 있음

```
Client (HTTPS) → Nginx (SSL 처리) → Backend (HTTP)
```

```
server {
    listen 443 ssl;
    server_name example.com;
    
    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;
    
    *# SSL 성능 최적화*
    ssl_session_cache shared:SSL:10m;   *# SSL 세션 재사용으로 핸드셰이크 생략*
    ssl_session_timeout 10m;
    
    location / {
        proxy_pass http://backend;      *# 내부는 HTTP로 통신*
    }
}
```

### 5. **HTTP 캐싱**

자주 요청되는 컨텐츠(API 응답, 정적 파일 등)를 Nginx의 메모리나 디스크에 캐싱해서, 동일한 요청이 들어오면 백엔드 서버에 요청하지 않고 바로 응답해주는 기능입니다.

**캐싱 전략:**

- **프록시 캐시**: 백엔드 API 응답을 캐싱
- **브라우저 캐시**: 클라이언트가 다시 요청하지 않도록 캐시 헤더 설정
- **CDN 캐시**: Nginx 자체를 CDN 노드로 활용

**성능 개선 효과:**

- 동일한 요청에 대해 응답 시간 **95% 단축** (예: 100ms → 5ms)
- 백엔드 서버 부하 **80% 감소**
- 네트워크 대역폭 절약

```
*# 프록시 캐시 설정*
proxy_cache_path /var/cache/nginx keys_zone=my_cache:10m max_size=1g;

location /api/products/ {
    proxy_cache my_cache;
    proxy_cache_valid 200 10m;         *# 성공 응답은 10분간 캐싱*
    proxy_cache_valid 404 1m;          *# 404 에러는 1분간 캐싱*
    proxy_cache_key "$request_method$request_uri$args";
    
    proxy_pass http://backend;
}

*# 정적 파일 브라우저 캐싱*
location ~* \.(jpg|jpeg|png|gif|css|js)$ {
    expires 1y;                        *# 1년간 브라우저 캐시*
    add_header Cache-Control "public, immutable";
}
```

### 6. **보안 처리**

**DDoS 방어, 스팸 차단, 접근 제어** 등의 보안 기능을 제공합니다. 애플리케이션 레벨에서 처리하기 어려운 네트워크 레벨의 보안 위협을 Nginx에서 미리 차단할 수 있습니다.

**주요 보안 기능:**

**6-1. IP 기반 접근 제어**

```
*# 특정 IP 차단*
location /admin/ {
    deny 192.168.1.100;
    deny 10.0.0.0/8;            *# IP 대역 차단*
    allow 203.241.132.0/24;     *# 회사 IP 대역만 허용*
    deny all;
}
```

**6-2. Rate Limiting (요청 수 제한)**
단시간에 과도한 요청을 보내는 클라이언트를 자동으로 차단하여 **DDoS 공격이나 무차별 대입 공격**을 방어합니다.

```
*# IP별로 초당 10개 요청만 허용*
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

location /api/ {
    limit_req zone=api burst=20 nodelay;    *# 순간적으로 20개까지 허용*
    limit_req_status 429;                   *# 제한 시 429 상태코드 응답*
}
```

**6-3. 대역폭 제한**

```
*# 클라이언트당 다운로드 속도 제한 (1MB/s)*
location /download/ {
    limit_rate 1m;
}
```

**6-4. 보안 헤더 추가**

```
*# 보안 강화 헤더들 자동 추가*
add_header X-Frame-Options "SAMEORIGIN";           *# 클릭재킹 방어*
add_header X-Content-Type-Options "nosniff";       *# MIME 스니핑 차단*
add_header X-XSS-Protection "1; mode=block";       *# XSS 필터 활성화*
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains";
```

---

위의 기능들을 실제 서비스를 운영할 때 필수적으로 사용하게 되는 기능들이다. 그렇기 때문에 Nginx를 필연적으로 많이 사용하게 되었다.

**실제 운영 환경에서의 활용 예:**

```
인터넷 → Nginx (80/443) → 내부 네트워크
         ↓
    ┌─────────┐  ┌─────────┐  ┌─────────┐
    │ Web App │  │ API 1   │  │ API 2   │
    │  :3000  │  │  :8080  │  │  :9000  │
    └─────────┘  └─────────┘  └─────────┘
```

이렇게 단일 진입점(Nginx)에서 SSL 처리, 로드밸런싱, 캐싱, 보안 등을 모두 처리하고, 백엔드 서버들은 비즈니스 로직에만 집중할 수 있게 됩니다.

## Apache 쓰면 안 되나요? 왜 굳이 Nginx를 써야 되는거죠?

## Apache vs Nginx: 아키텍처 차이점

Apache와 Nginx의 차이를 디테일하게 설명하면 내용이 어려워지고 재미없어진다. Nginx를 배우는 데 지금 이 내용은 크게 중요하지 않기 때문에 간단하게만 설명하겠다.

Nginx가 등장하기 전에는 대부분의 회사에서 Apache를 많이 사용했다. 그러나 근래에는 Nginx(25년 1월 기준 점유율 1위)의 사용량이 Apache(25년 1월 기준 점유율 2위)를 뛰어넘었다.

### 🔧 Apache의 아키텍처 한계

Apache는 **Process-based 또는 Thread-based** 아키텍처를 사용합니다:

### **Process-based 모델 (prefork 방식)**

각 클라이언트 연결마다 별도의 프로세스를 생성하여 처리하는 방식입니다.

**동작 방식:**

```
Master Process (Apache 관리자)
    ├── Child Process 1 → Client A 전담 처리
    ├── Child Process 2 → Client B 전담 처리  
    ├── Child Process 3 → Client C 전담 처리
    └── Child Process 4 → Client D 전담 처리
```

**특징:**

- **안정성 높음**: 한 프로세스가 크래시되어도 다른 프로세스에 영향 없음
- **메모리 사용량 높음**: 프로세스마다 독립적인 메모리 공간 필요 (보통 8~15MB)
- **Context Switching 오버헤드**: 프로세스 간 전환 시 CPU 비용 발생
- **확장성 제한**: 메모리 부족으로 동시 연결 수 제한

### **Thread-based 모델 (worker 방식)**

단일 프로세스 내에서 여러 스레드를 생성하여 각 클라이언트를 처리하는 방식입니다.

**동작 방식:**

```
Master Process
└── Worker Process
    ├── Thread 1 → Client A 처리
    ├── Thread 2 → Client B 처리
    ├── Thread 3 → Client C 처리
    └── Thread 4 → Client D 처리
```

**특징:**

- **메모리 효율성**: 스레드들이 메모리 공간 공유 (스레드당 약 2MB)
- **안정성 취약**: 하나의 스레드 문제가 전체 프로세스에 영향
- **동기화 복잡성**: 공유 자원 접근 시 lock 메커니즘 필요
- **스레드 풀 한계**: 미리 정의된 스레드 수만큼만 동시 처리 가능

**Process-based vs Thread-based 비교:**

```
Process-based:
메모리 사용량: 높음 (8MB × 연결수)
안정성: 높음
CPU 오버헤드: 높음 (Context Switching)

Thread-based:  
메모리 사용량: 중간 (2MB × 연결수)
안정성: 중간
CPU 오버헤드: 중간 (동기화 비용)
```

**공통 문제점:**

- 각 클라이언트 연결마다 새로운 프로세스/스레드 생성
- 메모리 사용량이 연결 수에 비례하여 증가
- Context Switching 오버헤드 발생
- **C10K 문제**: 동시 연결 1만개 처리 시 심각한 성능 저하

```
Apache 처리 방식:
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  Process 1  │    │  Process 2  │    │  Process 3  │
│ (Client A)  │    │ (Client B)  │    │ (Client C)  │
└─────────────┘    └─────────────┘    └─────────────┘

실제 리소스 사용량:
- 1,000명 동시 접속 시
- Process 모드: 1,000개 프로세스 × 8MB = 8GB 메모리
- Thread 모드: 1,000개 스레드 × 2MB = 2GB 메모리
```

### ⚡ Nginx의 혁신적 아키텍처

Nginx는 **Event-driven, Non-blocking I/O** 방식을 채택:

### **Event-driven 아키텍처**

전통적인 "연결당 프로세스/스레드" 모델을 버리고, **이벤트 기반으로 비동기 처리**하는 방식입니다.

**핵심 개념:**

- **단일 스레드 이벤트 루프**: 각 워커 프로세스는 하나의 이벤트 루프로 수천 개 연결 처리
- **Non-blocking I/O**: 파일 읽기, 네트워크 통신 등에서 대기하지 않고 다른 작업 수행
- **비동기 처리**: 작업 완료를 기다리는 동안 다른 클라이언트 요청 처리

**동작 방식:**

```
Nginx Event-driven 처리:
┌─────────────────────────────────────────┐
│            Master Process               │ ← 설정 관리, 워커 프로세스 관리
├─────────────────────────────────────────┤
│  Worker 1  │  Worker 2  │  Worker 3    │ ← CPU 코어 수만큼 생성
│ Event Loop │ Event Loop │ Event Loop   │ ← 각각 독립적인 이벤트 루프
│ ┌────────┐ │ ┌────────┐ │ ┌────────┐   │
│ │Client A│ │ │Client D│ │ │Client G│   │ ← 하나의 워커가 여러 클라이언트 처리
│ │Client B│ │ │Client E│ │ │Client H│   │
│ │Client C│ │ │Client F│ │ │Client I│   │
│ └────────┘ │ └────────┘ │ └────────┘   │
└─────────────────────────────────────────┘
```

**이벤트 루프 처리 과정:**

```
1. 새로운 연결 요청 → 이벤트 큐에 등록
2. 파일 읽기 요청 → 비동기로 시작하고 다음 작업으로 이동  
3. 데이터 전송 준비 완료 → 이벤트 발생, 응답 처리
4. 연결 종료 → 리소스 정리

하나의 워커가 동시에 처리:
- 1000개 연결 대기
- 50개 파일 읽기 중
- 200개 데이터 전송 중  
- 모두 단일 스레드에서!
```

**핵심 장점:**

- **적은 메모리 사용**: 워커 프로세스 수는 CPU 코어 수와 동일하게 유지
- **높은 동시 접속 처리**: 단일 워커가 수천 개의 연결을 비동기로 처리
- **Context Switching 최소화**: 프로세스/스레드 생성 오버헤드 없음
- **CPU 효율성**: 대기 시간 없이 항상 유용한 작업 수행

**Apache vs Nginx 아키텍처 비교:**

```
Apache (Thread-based):
Thread 1: Client A 요청 → 파일 읽기 대기 → 블록됨
Thread 2: Client B 요청 → DB 쿼리 대기 → 블록됨  
Thread 3: Client C 요청 → 네트워크 응답 대기 → 블록됨

Nginx (Event-driven):
Worker 1: Client A 파일 읽기 시작 → Client B 처리 시작 → 
         Client C 응답 전송 → Client A 파일 읽기 완료 처리
```

**실제 리소스 사용량 비교:**

```
*# Apache (prefork 모드) - 1,000명 동시 접속*
1,000개 프로세스 × 8MB = 8GB 메모리

*# Apache (worker 모드) - 1,000명 동시 접속*  
1,000개 스레드 × 2MB = 2GB 메모리

*# Nginx - 1,000명 동시 접속*
4개 워커 프로세스 × 10MB = 40MB 메모리
```

Nginx를 더 많이 사용하는 가장 큰 이유는 Apache에 비해 훨씬 많은 트래픽을 처리할 수 있는 구조를 가지고 있었기 때문이다. 즉, Nginx가 Apache보다 훨씬 성능이 좋았던 것이다. 이런 이유 때문에 최근 기업에서는 Apache보다 Nginx를 선호하게 되었다.

## 🚀 성능 비교 분석

### 메모리 사용량

```
*# Apache (prefork 모드)*
동시 연결 1,000개 = 약 1,000개 프로세스 × 8MB = 8GB 메모리

*# Nginx*
동시 연결 1,000개 = 4개 워커 프로세스 × 10MB = 40MB 메모리
```

### 처리량 비교 (벤치마크)

- **Apache**: 초당 2,000~5,000 요청 처리
- **Nginx**: 초당 50,000+ 요청 처리 가능

## 🛠️ Nginx가 특히 강한 영역들

### 1. 정적 컨텐츠 제공

```
*# Nginx는 sendfile() 시스템 콜 최적화*
location /static/ {
    sendfile on;           *# 커널 레벨에서 파일 전송*
    tcp_nopush on;         *# TCP 패킷 효율성 증대*
    expires 1y;            *# 브라우저 캐싱 활용*
}
```

### 2. 리버스 프록시 & 로드밸런싱

```
upstream backend {
    server app1:8080 weight=3;
    server app2:8080 weight=2;
    server app3:8080 backup;    *# 장애 시 대체 서버*
}

server {
    location / {
        proxy_pass http://backend;
        proxy_connect_timeout 1s;   *# 빠른 장애 감지*
        proxy_read_timeout 30s;
    }
}
```

### 3. SSL/TLS 처리 최적화

```
*# SSL 세션 재사용으로 핸드셰이크 오버헤드 감소*
ssl_session_cache shared:SSL:10m;
ssl_session_timeout 10m;
ssl_stapling on;              *# OCSP Stapling으로 인증서 검증 빠르게*
```

## 🔍 Apache가 여전히 유리한 경우

**확실하지 않음**이라고 명시하지만, 다음 상황에서는 Apache가 더 적합할 수 있습니다:

1. **동적 컨텐츠 중심**: PHP 모듈 방식으로 처리할 때
2. **레거시 애플리케이션**: .htaccess 파일 의존성이 높은 경우
3. **소규모 서비스**: 복잡한 설정이 불필요한 경우

## 💡 결론

Nginx의 우위는 단순히 "성능이 좋다"는 표면적인 이유가 아니라, **현대 웹 서비스의 요구사항**(높은 동시 접속, 낮은 지연시간, 효율적 자원 활용)에 최적화된 아키텍처를 가지고 있기 때문입니다.

특히 마이크로서비스 아키텍처, 컨테이너 환경, 클라우드 네이티브 애플리케이션에서 Nginx는 **API Gateway, 로드밸런서, SSL 터미네이션** 역할을 효율적으로 수행할 수 있어 필수적인 인프라 컴포넌트가 되었습니다.
