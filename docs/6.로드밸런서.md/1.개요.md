## 🎯 로드 밸런서란 무엇인가?

서비스를 운영하다보면 점점 많은 트래픽(부하)이 발생해 한 대의 서버로는 사양이 부족한 경우가 발생합니다. 이를 해결하기 위해 서버를 여러 대로 늘려 운영하지만, 사용자에게 여러 서버에 골고루 알아서 요청을 보내라고 할 수는 없습니다.

- *로드 밸런서(Load Balancer)**는 들어오는 사용자의 요청(트래픽)을 여러 대의 웹 애플리케이션 서버에 효율적으로 분산시키는 네트워크 장비 또는 소프트웨어입니다.

### 📋 핵심 목적

1. **가용성(Availability) 향상** - 서버 장애 시 다른 서버로 트래픽 전환
2. **확장성(Scalability) 제공** - 수평적 스케일링 지원
3. **성능 최적화** - 부하 분산을 통한 응답 시간 개선
4. **단일 장애점(SPOF) 제거** - 한 서버 장애가 전체 서비스에 미치는 영향 최소화

## 🌐 네트워크 관점에서의 로드 밸런싱

### OSI 7계층과 로드 밸런서 분류

로드 밸런서는 OSI 모델의 어느 계층에서 동작하느냐에 따라 분류됩니다:

```
7. Application Layer    ← L7 로드 밸런서 (HTTP, HTTPS)
6. Presentation Layer
5. Session Layer  
4. Transport Layer      ← L4 로드 밸런서 (TCP, UDP)
3. Network Layer        ← L3 로드 밸런서 (IP 기반)
2. Data Link Layer      ← L2 로드 밸런서 (MAC 기반)
1. Physical Layer
```

### L4 로드 밸런서 (Layer 4 - Transport Layer)

```
TCP/UDP 헤더 분석:
[IP Header] [TCP: Src Port=12345, Dst Port=80, SEQ, ACK...] [Data]

포트 기반 분배:
:80   → Web Server Pool
:443  → HTTPS Server Pool
:3306 → Database Pool
```

- **작동 방식**: IP주소와 포트 기반으로 트래픽 분배
- **특징**: TCP/UDP 레벨에서 동작, 빠른 처리 속도
- **장점**: 높은 성능, 낮은 지연시간
- **한계**: HTTP 헤더나 쿠키 정보 활용 불가

### L7 로드 밸런서 (Layer 7 - Application Layer)

```
HTTP 요청 전체 분석:
GET /api/v1/users HTTP/1.1
Host: api.example.com
User-Agent: Mozilla/5.0
Cookie: session_id=abc123
Content-Type: application/json

라우팅 규칙:
/api/v1/* → API Server Pool
/static/* → CDN Server Pool
Cookie에 따른 → Sticky Session
```

- **작동 방식**: HTTP 헤더, URL, 쿠키 등 애플리케이션 정보 기반 분배
- **특징**: 더 세밀한 제어 가능, SSL 종료 처리 가능
- **활용**: API 버전별 라우팅, A/B 테스트, 콘텐츠 기반 라우팅

## 🔧 로드 밸런싱 알고리즘

### 1. Round Robin (라운드 로빈)

```
요청1 → 서버A
요청2 → 서버B
요청3 → 서버C  
요청4 → 서버A (다시 순환)
```

- **특징**: 가장 단순하고 공평한 분배
- **적용**: 서버 성능이 동일할 때 효과적

### 2. Weighted Round Robin (가중 라운드 로빈)

```
서버A (가중치: 3) - 고성능 서버
서버B (가중치: 2) - 중간 성능 서버
서버C (가중치: 1) - 저성능 서버

→ A, A, A, B, B, C 순서로 분배
```

- **특징**: 서버 성능에 따른 차등 분배
- **적용**: 서버 사양이 다를 때 유용

### 3. Least Connections (최소 연결)

- **동작**: 현재 활성 연결 수가 가장 적은 서버로 요청 전달
- **적용**: 연결 지속 시간이 다양한 서비스

### 4. IP Hash

- **동작**: 클라이언트 IP를 해시하여 특정 서버로 고정 분배
- **적용**: 세션 유지가 중요한 경우

## 🚀 네트워크 패킷 흐름과 구현 방식

### 일반적인 Proxy 방식 흐름

```
Client → Load Balancer → Backend Server

Phase 1: Client → LB
DNS: example.com → 203.0.113.10 (LB VIP)
TCP: Client:12345 → LB:80

Phase 2: LB → Backend
Source NAT: LB → Backend  
TCP: LB:45678 → Backend:8080

Phase 3: 응답 경로
Backend → LB → Client (같은 경로로 역순)
```

### Direct Server Return (DSR) 방식

```
Request:  [Client] → [LB] → [Backend]
Response: [Backend] ────────→ [Client]
          (응답은 LB 우회, 성능 향상)
```

## 🛠️ 실제 구현: Nginx 로드 밸런싱

### 기본 설정

```
upstream backend_servers {
    server 192.168.1.10:8080 weight=3;
    server 192.168.1.11:8080 weight=2;
    server 192.168.1.12:8080 weight=1;
    server 192.168.1.13:8080 backup;  *# 백업 서버*
}

server {
    listen 80;
    server_name example.com;
    
    location / {
        proxy_pass http://backend_servers;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### 고급 라우팅 설정 (L7 기능)

```
upstream api_servers {
    server 10.0.1.10:8080;
    server 10.0.1.11:8080;
}

upstream static_servers {
    server 10.0.2.10:80;
    server 10.0.2.11:80;
}

server {
    listen 80;
    
    *# API 요청은 API 서버로*
    location /api/ {
        proxy_pass http://api_servers;
    }
    
    *# 정적 파일은 정적 서버로*
    location /static/ {
        proxy_pass http://static_servers;
    }
    
    *# 기본 요청*
    location / {
        proxy_pass http://api_servers;
    }
}
```

### 헬스 체크와 장애 처리

```
upstream backend_servers {
    server 192.168.1.10:8080 max_fails=3 fail_timeout=30s;
    server 192.168.1.11:8080 max_fails=3 fail_timeout=30s;
    
    *# 헬스 체크 설정*
    keepalive 32;  *# 연결 풀 유지*
}
```

## 🔍 세션 관리와 상태 유지

### Sticky Session (Session Affinity)

```
upstream backend {
    ip_hash;  *# IP 기반 고정 분배*
    server 10.0.1.10:8080;
    server 10.0.1.11:8080;
}
```

### Stateless 설계 (권장)

```
Session Store 분리:
[Client] → [LB] → [Any Backend Server]
                      ↓
                  [Redis/DB] (공유 세션 저장소)
```

## ⚡ 성능 최적화 기법

### Connection Multiplexing

```
upstream backend {
    server 10.0.1.10:8080;
    keepalive 32;  *# LB-Backend 간 연결 풀 유지*
}

location / {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";  *# Keep-Alive 활성화*
}
```

### SSL/TLS 최적화

```
server {
    listen 443 ssl http2;
    
    *# SSL 종료 (SSL Termination)*
    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;
    
    *# Backend은 평문 통신*
    location / {
        proxy_pass http://backend_servers;
    }
}
```

## 🏢 대규모 환경에서의 다층 구조

### Multi-Tier Load Balancing

```
Internet
    ↓
[Global Load Balancer] (DNS 기반, GeoDNS)
    ↓
[Regional Load Balancer] (L4, 하드웨어 - F5, A10 등)
    ↓
[Application Load Balancer] (L7, 소프트웨어 - Nginx, HAProxy)
    ↓
[Backend Server Pool]
```

### 실제 아키텍처 예시

```
사용자 요청 흐름:
1. DNS: example.com → Global LB IP
2. Global LB: 지역별 최적 Regional LB 선택
3. Regional LB: L4 레벨에서 빠른 분산
4. Application LB: 비즈니스 로직에 따른 라우팅
5. Backend Server: 실제 요청 처리
```

## 📊 모니터링과 운영

### 핵심 모니터링 지표

```bash
*# 연결 상태 모니터링*
netstat -an | grep :80 | wc -l              *# 현재 연결 수*
ss -tuln                                     *# 리스닝 포트 확인# Nginx 상태 확인*
curl http://localhost/nginx_status

*# Backend 서버 상태*
upstream_check 모듈 사용 또는 별도 헬스체크 도구
```

### 장애 대응 시나리오

```bash
1. Backend 서버 장애:
   - 자동 헬스체크로 트래픽 차단
   - 남은 서버로 자동 분산
   
2. Load Balancer 장애:
   - VRRP/keepalived로 Failover
   - VIP 이동으로 투명한 전환
   
3. 전체 Backend Pool 장애:
   - 미리 정의된 에러 페이지 표시
   - Graceful degradation
```

## 💡 실제 운영 시 고려사항

### 1. 용량 계획 (Capacity Planning)

- **현재 트래픽 분석**: 피크 시간대, 평균 동시접속자 수
- **성장률 고려**: 향후 6개월~1년 트래픽 증가 예측
- **서버 리소스**: CPU, 메모리, 네트워크 대역폭

### 2. 보안 고려사항

```bash
*# DDoS 방어*
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
limit_req zone=api burst=20 nodelay;

*# 실제 클라이언트 IP 보존*
real_ip_header X-Forwarded-For;
set_real_ip_from 10.0.0.0/8;
```

### 3. 로그 관리

```bash
log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                '$status $body_bytes_sent "$http_referer" '
                '"$http_user_agent" "$http_x_forwarded_for" '
                'upstream_addr=$upstream_addr '
                'upstream_response_time=$upstream_response_time';
```

로드 밸런서는 단순히 트래픽을 분산하는 도구가 아니라, **전체 시스템 아키텍처의 핵심 구성요소**입니다. 네트워크 레벨의 깊은 이해와 함께 비즈니스 요구사항을 고려한 설계가 중요합니다.
