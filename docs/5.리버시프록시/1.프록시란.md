# 프록시 서버와 네트워크 아키텍처 심화 가이드

## 프록시(Proxy)란?

**프록시(Proxy)**란 '**중계(중간에서 연결해주는 것)**'의 의미를 가진다.

그러면 **프록시 서버(Proxy Server)**는 **중간 역할을 해주는 서버**다. 클라이언트(사용자)와 서버가 직접 통신하지 않고 **중간 역할을 하는 서버**를 거쳐서 통신을 하고 있다. 여기서 **중간 역할을 하는 서버**를 보고 **프록시 서버(Proxy Server)**라고 부른다.

그래서 클라이언트가 직접 WAS와 통신하지 않고 중간에 nginx를 거쳐서 서로 통신을 하는 리버스의 역할도 nginx는 가능하다. 그래서 하나의 EC2 혹은서버에 프록시 서버와 WAS서버를 같이 구성할 수 있고 따로 구성할 수도 있다.

### 네트워크 계층 관점에서 본 프록시

프록시가 "중간 역할"을 한다는 것을 네트워크 관점에서 더 자세히 살펴보면, **OSI 7계층 중 Application Layer(7계층)에서 동작**한다는 것을 알 수 있습니다.

```
[클라이언트] ←→ [프록시 서버] ←→ [실제 서버]
     ↓              ↓              ↓
Application    Application    Application
Presentation   Presentation   Presentation  
Session        Session        Session
Transport      Transport      Transport     ← TCP 연결 종료/시작
Network        Network        Network       ← IP 라우팅 처리
Data Link      Data Link      Data Link
Physical       Physical       Physical
```

**중요한 점**: 프록시 서버는 **TCP 연결을 두 번 처리**합니다.
- **연결 1**: 클라이언트 ↔ 프록시 서버
- **연결 2**: 프록시 서버 ↔ 실제 서버

이는 단순히 패킷을 전달하는 라우터와 다르게, HTTP 요청을 완전히 받아서 해석한 후 새로운 요청을 만들어 전송하기 때문입니다.

### IP 주소와 포트 관점에서의 변화

**직접 연결 시:**
```
클라이언트(192.168.1.100:54321) → 서버(203.123.45.67:80)
```

**프록시를 통한 연결 시:**
```
클라이언트(192.168.1.100:54321) → 프록시(10.0.0.50:80)
프록시(10.0.0.50:34567) → 실제서버(192.168.10.100:8080)
```

실제 서버는 클라이언트의 실제 IP를 모르고 프록시 서버의 IP만 알게 됩니다. 이때 클라이언트의 실제 정보를 전달하기 위해 **HTTP 헤더**를 활용합니다:

```http
X-Forwarded-For: 192.168.1.100
X-Real-IP: 192.168.1.100
X-Forwarded-Proto: https
```

## 포워드 프록시(Forward Proxy)란?

**보내려고 하는 요청**을 **관리** 또는 **보안 처리**를 위한 용도로 사용하는 서버를 **포워드 프록시(Foward Proxy) 서버**라고 얘기를 한다. 포워드 프록시 서버의 대표적인 예시로 **회사 방화벽**이 있다. 회사 내부에 있는 컴퓨터로 ChatGPT에 접속하려는데 차단되는 경우가 있다. 포워드 프록시 서버가 보내려고 하는 요청을 감시하면서 위험하다고 판단되는 사이트에 접속하지 못하게 차단 설정을 한 것이다.
즉 내부망 사용자가 인터넷을 나가기전에 포워드 프록시를 거쳐서 나가게된다.

### 네트워크 토폴로지 관점에서 본 포워드 프록시

```
[내부망]                    [DMZ]                [외부 인터넷]
클라이언트들 → 포워드 프록시 → 방화벽 → 인터넷 서비스들
(사내 PC)     (보안 정책)    (경계)    (웹사이트들)
```

포워드 프록시는 **내부망에서 외부로 나가는 트래픽을 제어**하는 역할을 합니다. 이때 프록시 서버는 **게이트웨이의 역할**을 하며, 단순한 라우팅이 아닌 **애플리케이션 레벨에서의 정책 적용**이 가능합니다.

### 포워드 프록시의 심화 기능들

#### 1. **컨텐츠 필터링 (Content Filtering)**
회사에서 특정 사이트를 차단하는 것 외에도:
```nginx
# nginx 포워드 프록시 설정 예시
server {
    listen 8080;
    resolver 8.8.8.8;
    
    location / {
        # 차단된 사이트 필터링
        if ($http_host ~* "(facebook|youtube)\.com") {
            return 403 "Access Denied by Company Policy";
        }
        
        proxy_pass $scheme://$http_host$request_uri;
    }
}
```

#### 2. **캐싱으로 대역폭 절약**
자주 접속하는 사이트의 리소스를 캐시해서 인터넷 트래픽을 줄일 수 있습니다:
```http
# 캐시 가능 여부 판단
Cache-Control: max-age=3600, public
ETag: "abc123def456"
```

#### 3. **대역폭 제어**
특정 사용자나 서비스의 인터넷 사용량을 제한할 수 있습니다:
```nginx
limit_rate 100k;  # 100KB/s로 제한
```

## 리버스 프록시(Reverse Proxy)란?

**들어오는 요청**을 **관리** 또는 **보안 처리**를 하기 위한 용도로 사용하는 서버를 **리버스 프록시(Reverse Proxy) 서버**라고 얘기를 한다. 리버스 프록시 서버의 대표적인 예시가 **HTTPS 처리, 요청 수 제한, 로드 밸런싱을 하는 용도로 사용하는 Nginx**가 있다. 리버스 프록시 서버가 들어오는 요청의 보안 처리를 하기 위해 HTTPS 처리를 한다. 그리고 들어오는 요청을 감시하다가 일정 요청 수 이상을 보낼 때도 차단을 하게끔 설정할 수 있다. 또한 들어오는 요청을 여러 대의 서버로 분배해주는 역할인 로드밸런싱 기능을 하게끔 셋팅할 수 있다.

### 네트워크 아키텍처 관점에서 본 리버스 프록시

```
[인터넷] → [리버스 프록시] → [내부 서버들]
          (Load Balancer)    (Web Server Farm)
             └─ SSL 종료
             └─ 캐싱        
             └─ 압축
             └─ 보안 필터링
```

리버스 프록시는 **외부에서 내부로 들어오는 트래픽을 제어**하며, **웹 애플리케이션 게이트웨이** 역할을 합니다.

### HTTPS 처리의 네트워크적 의미

HTTPS 처리를 리버스 프록시에서 담당한다는 것은 **SSL/TLS 터미네이션**을 의미합니다:

```nginx
server {
    listen 443 ssl http2;
    
    # SSL 인증서 설정
    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/private.key;
    
    # 백엔드로는 HTTP로 전달 (SSL 부하 제거)
    location / {
        proxy_pass http://backend_servers;
        
        # 원본 정보 전달
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

이렇게 하면 **백엔드 서버들은 SSL 처리 부담 없이 비즈니스 로직에만 집중**할 수 있습니다.

### 로드 밸런싱의 다양한 알고리즘

"여러 대의 서버로 분배"하는 방법에는 여러 알고리즘이 있습니다:

```nginx
upstream backend_servers {
    # 라운드 로빈 (순차적 분배)
    server 192.168.1.10:8080 weight=3;
    server 192.168.1.11:8080 weight=2;
    
    # 세션 유지를 위한 IP 해시
    ip_hash;
    
    # 헬스 체크
    server 192.168.1.12:8080 backup;
}
```

### 요청 수 제한(Rate Limiting)의 구현

"일정 요청 수 이상 차단"하는 기능:

```nginx
# 초당 10개 요청으로 제한
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

server {
    limit_req zone=api burst=20 nodelay;
    
    location / {
        proxy_pass http://backend_servers;
    }
}
```

## 리버스 프록시(Reverse Proxy)는 왜 활용할까?

**들어오는 요청**을 **관리** 또는 **보안 처리**를 하기 위해 사용한다. 만약 리버스 프록시 서버를 사용하지 않고 직접적으로 들어오는 요청을 백엔드 서버가 바로 받아 처리하는 식으로 구성하면 보안적으로 문제되는 경우가 많다. 가장 대표적인 예시로 누군가가 악의적으로 수많은 요청을 갑자기 보내는 경우, 실제 백엔드 서버가 그 요청을 다 받아서 처리하려고 하기 때문에 과부하가 걸려 서버 장애가 발생한다.

### 네트워크 보안 경계 설정

리버스 프록시를 사용하는 이유를 네트워크 보안 관점에서 보면:

```
[외부 인터넷] → [DMZ - 리버스 프록시] → [내부망 - 애플리케이션 서버들]
                      ↓
                  - 방화벽 역할
                  - SSL 터미네이션  
                  - 로그 수집
                  - 침입 탐지
```

**직접 연결 시의 위험:**
- 백엔드 서버의 IP 주소가 외부에 노출
- 애플리케이션 서버가 모든 공격을 직접 받음
- 각 서버마다 개별적으로 보안 설정 필요

**리버스 프록시 사용 시:**
- 백엔드 서버는 내부망에서 보호됨
- 공격 트래픽을 프록시에서 사전 차단
- 중앙화된 보안 정책 적용 가능

### DDoS 공격 방어 메커니즘

"수많은 요청을 갑자기 보내는" DDoS 공격을 방어하는 방법:

```nginx
# 1. Connection 제한
limit_conn_zone $binary_remote_addr zone=addr:10m;
limit_conn addr 10;  # IP당 최대 10개 연결

# 2. 요청 속도 제한
limit_req_zone $binary_remote_addr zone=req:10m rate=5r/s;
limit_req zone=req burst=10 nodelay;

# 3. 악성 패턴 차단
location / {
    # SQL Injection 패턴 차단
    if ($args ~* "(union|select|insert|delete)") {
        return 403;
    }
    
    proxy_pass http://backend;
}
```

### 장애 격리 (Fault Isolation)

```nginx
upstream backend {
    server app1:8080 max_fails=3 fail_timeout=30s;
    server app2:8080 max_fails=3 fail_timeout=30s;
    server app3:8080 backup;  # 장애 시 자동 전환
}
```

한 서버에 장애가 발생해도 프록시가 자동으로 정상 서버로 트래픽을 우회시켜 **전체 서비스의 가용성을 보장**합니다.

## 프록시 vs 스위치 vs 게이트웨이

프록시가 "중간 역할"을 한다고 했는데, 네트워크 장비들과 어떤 차이가 있을까요?

### 비교표

| 구분 | OSI 계층 | 역할 | 처리 방식 | 예시 |
|------|----------|------|-----------|------|
| **스위치** | 2계층 | MAC 주소 기반 프레임 전달 | 투명한 전달 | L2 스위치 |
| **라우터** | 3계층 | IP 주소 기반 패킷 라우팅 | 헤더만 확인 | 공유기, L3 스위치 |
| **프록시** | 7계층 | 애플리케이션 데이터 처리 | 완전한 해석/수정 | Nginx, Squid |

### 결론: 프록시는 Application Gateway

**프록시 서버는 스위치가 아니라 게이트웨이입니다!** 구체적으로는 **"Application Gateway"** 또는 **"웹 애플리케이션 게이트웨이"**입니다.

**왜 게이트웨이인가?**
1. **서로 다른 네트워크 영역을 연결** (클라이언트 네트워크 ↔ 서버 네트워크)
2. **프로토콜 변환 가능** (HTTP → HTTPS, HTTP/1.1 → HTTP/2)
3. **보안 경계 역할** (내부망과 외부망 사이)
4. **서비스 추상화** (클라이언트는 실제 서버 구조를 모름)

## 실제 운영 환경에서의 프록시 활용

### 다중 계층 구조

실제 서비스에서는 여러 종류의 프록시를 조합해서 사용합니다:

```
[클라이언트]
    ↓
[CDN (Cloudflare, AWS CloudFront)]  ← 글로벌 엣지 캐싱
    ↓
[Application Load Balancer]         ← AWS ALB, NGINX Plus
    ↓
[리버스 프록시 (NGINX)]             ← SSL 터미네이션, 캐싱
    ↓
[애플리케이션 서버들]               ← 실제 비즈니스 로직 (WAS)
```

### 마이크로서비스 환경에서의 API Gateway

```nginx
# API Gateway 역할의 리버스 프록시
location /user-service/ {
    proxy_pass http://user-service-cluster/;
}

location /order-service/ {
    proxy_pass http://order-service-cluster/;
}

location /payment-service/ {
    proxy_pass http://payment-service-cluster/;
}
```

이렇게 프록시는 단순한 "중간 역할"을 넘어서 **현대 웹 아키텍처의 핵심 구성요소**로서 보안, 성능, 확장성을 모두 책임지는 중요한 역할을 합니다.
