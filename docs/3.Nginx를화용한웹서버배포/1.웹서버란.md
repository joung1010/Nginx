## 웹서버란?

우리는 어떻게 네이버에 접속할 수 있는걸까??? 예를 들어 우리가 네이버 접속하기위에 `www.naver.com` 이라는 주소를 브라우저에 입력하게 되면 네이버라는 웹사이트를 찾아들어가는 것처럼 보이지만 실제로는 훨씬 복잡한 과정을 거치게 됩니다.

### 🌐 실제 웹 접속 과정 (네트워크 관점)

**1단계: DNS 해석 (Domain Name Resolution)**

```
www.naver.com → DNS 서버 조회 → 223.130.195.200 (실제 IP 주소)
```

브라우저는 먼저 도메인명을 실제 서버의 IP 주소로 변환해야 합니다. 이 과정에서 여러 DNS 서버를 거쳐가며 최종적으로 네이버 서버의 실제 IP 주소를 찾아냅니다.

**2단계: TCP 연결 설정 (3-Way Handshake)**

```
클라이언트 → SYN → 서버
클라이언트 ← SYN+ACK ← 서버  
클라이언트 → ACK → 서버
연결 성립!
```

**3단계: HTTP 요청 전송**

http

```
GET / HTTP/1.1
Host: www.naver.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Accept: text/html,application/xhtml+xml
Accept-Language: ko-KR,ko;q=0.9
```

**4단계: 서버 응답**

http

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 145234
Date: Sat, 30 Aug 2025 12:00:00 GMT

<!DOCTYPE html>
<html>
<head>...</head>
<body>...</body>
</html>
```

브라우저에 주소를 입력하는 순간 네이버 웹사이트로 접속하는게 아니라, **네이버 서버로부터 HTML, CSS, JS파일들을 HTTP 프로토콜을 통해 다운로드 받는 방식**이다. 그리고 그 다운로드 받은 파일의 코드를 브라우저가 해석해서 화면에 보여주는 것이다.

### 📡 네트워크 계층에서의 웹 서버

**웹 서버의 네트워크 역할:**

```
OSI 7계층 관점:
┌─────────────────┐
│ 7. Application  │ ← HTTP/HTTPS 프로토콜 처리
├─────────────────┤
│ 6. Presentation │ ← SSL/TLS 암복호화
├─────────────────┤  
│ 5. Session      │ ← HTTP 세션 관리
├─────────────────┤
│ 4. Transport    │ ← TCP 연결 관리
└─────────────────┘
```

웹 서버는 단순히 파일을 제공하는 것이 아니라 **HTTP 프로토콜의 서버 구현체**입니다. 클라이언트(브라우저)와 서버 간의 통신 규약을 정의하고 실행하는 소프트웨어인 것입니다.

### 🔄 동시 연결 처리의 복잡성

실제 웹 서버는 하나의 클라이언트만 상대하는 것이 아닙니다:

```
실시간 상황 (네이버 서버):
├── 사용자 A: 메인 페이지 요청 중
├── 사용자 B: 이미지 파일 다운로드 중  
├── 사용자 C: 뉴스 기사 읽기 중
├── 사용자 D: 검색 요청 처리 중
└── ... (수만 명이 동시 접속)
```

이때 웹 서버는 **각각의 연결을 독립적으로 관리**하면서 동시에 처리해야 합니다. 여기서 Apache와 Nginx의 차이가 드러나게 됩니다.

### 🏢 웹 서버의 물리적 구성

**하드웨어 관점:**

```
인터넷 → 방화벽 → 로드밸런서 → 웹 서버 클러스터
                                ├── Web Server 1 (Nginx)
                                ├── Web Server 2 (Nginx)  
                                └── Web Server 3 (Nginx)
```

**소프트웨어 관점:**

```
운영체제 (Linux/Windows)
├── 웹 서버 소프트웨어 (Nginx/Apache)
├── 네트워크 스택 (TCP/IP)
└── 파일 시스템 (정적 파일 저장)
```

### 💾 포트와 소켓 관리

웹 서버는 특정 포트(보통 80번, 443번)에서 **리스닝(Listening)** 상태로 대기하고 있습니다:

```bash
*# 웹 서버가 열어둔 포트 확인*
netstat -tlnp | grep nginx
tcp  0  0  0.0.0.0:80   0.0.0.0:*  LISTEN  1234/nginx
tcp  0  0  0.0.0.0:443  0.0.0.0:*  LISTEN  1234/nginx
```

각 클라이언트 연결은 고유한 **소켓(Socket)**으로 관리됩니다:

```
서버 소켓: 223.130.195.200:80
├── 클라이언트 1: 192.168.1.100:52341  
├── 클라이언트 2: 192.168.1.101:52342
└── 클라이언트 3: 192.168.1.102:52343
```

위에서 네이버에 접속할 수 있는 방식에 대해 알아봤다. 네이버의 서버가 HTML, CSS, JS, 이미지와 같은 파일들을 사용자들이 다운받을 수 있게 제공하고 있었다.

> 이 예시를 기반으로 웹 서버(Web Server)의 의미를 정리해보자.
>
- *웹 서버(Web Server)**는 **사용자의 요청([www.naver.com으로](http://www.naver.xn--com-ky7m580d/) 접속하는 행위)이 들어올 때마다 HTML, CSS, JS, 이미지와 같은 파일들을 HTTP 프로토콜을 통해 제공하는 컴퓨터 또는 소프트웨어**를 의미한다.

### 🔧 웹 서버의 핵심 작업들

### **1. 요청 파싱 (Request Parsing)**

클라이언트가 보낸 HTTP 요청을 분석하여 어떤 파일을 원하는지 파악:

```
GET /images/logo.png HTTP/1.1
Host: www.naver.com
↓
파일 경로: /var/www/html/images/logo.png
```

### **2. 파일 시스템 접근**

요청된 파일이 서버의 어느 위치에 있는지 찾고 읽기:

```
URL: /images/logo.png  
→ 실제 경로: /var/www/html/images/logo.png
→ 파일 존재 여부 확인
→ 권한 확인 (읽기 가능한가?)
→ 파일 읽기
```

### **3. HTTP 응답 생성**

적절한 HTTP 헤더와 함께 파일 내용을 응답으로 만듭니다:

```
HTTP/1.1 200 OK
Content-Type: image/png
Content-Length: 15420
Last-Modified: Fri, 29 Aug 2025 10:30:00 GMT
Cache-Control: max-age=3600

[이미지 바이너리 데이터]
```

### **4. 네트워크 전송**

만들어진 응답을 TCP 소켓을 통해 클라이언트로 전송합니다.

### Nginx의 웹 서버(Web Server) 기능

Nginx는 웹 서버(Web Server) 역할을 할 수 있다. 풀어서 설명하자면 Nginx가 사용자의 요청이 들어올 때마다 파일(HTML, CSS, JS, 이미지 등)을 제공할 수 있는 기능을 가지고 있다. 따라서 Nginx를 활용하면 웹 사이트를 배포할 수 있다.

### 🚀 Nginx 웹 서버의 고급 기능들

**1. MIME 타입 자동 인식**
파일 확장자에 따라 적절한 Content-Type 헤더를 자동으로 설정:

nginx

```
location ~* \.(jpg|jpeg|png|gif)$ {
    expires 1y;
    add_header Content-Type image/jpeg;
}

location ~* \.(css)$ {
    expires 1y;  
    add_header Content-Type text/css;
}
```

**2. 압축 전송 (Gzip)**
파일을 압축해서 전송하여 네트워크 대역폭을 절약:

```
gzip on;
gzip_comp_level 6;
gzip_types text/html text/css application/javascript;

*# 결과: 100KB 파일 → 25KB로 압축 전송*
```

**3. 범위 요청 처리 (Range Requests)**
대용량 파일의 일부분만 다운로드할 수 있게 지원:

```
Request: Range: bytes=1024-2047
Response: Content-Range: bytes 1024-2047/10485760
```

**4. 가상 호스트 (Virtual Hosts)**
하나의 서버에서 여러 도메인을 처리:

nginx

```
*# example.com 처리*
server {
    server_name example.com;
    root /var/www/example;
}

*# blog.com 처리*  
server {
    server_name blog.com;
    root /var/www/blog;
}
```

### 🏗️ 웹 서버 vs 애플리케이션 서버

**웹 서버 (Nginx, Apache)**

- **역할**: 정적 파일 제공, HTTP 요청/응답 처리
- **처리 대상**: HTML, CSS, JS, 이미지, 동영상 등
- **특징**: 빠른 파일 서빙, 높은 동시 접속 처리

**애플리케이션 서버 (Tomcat, WAS)**

- **역할**: 동적 컨텐츠 생성, 비즈니스 로직 실행
- **처리 대상**: JSP, Servlet, 데이터베이스 연동 등
- **특징**: 프로그래밍 언어 실행 환경 제공

**실제 운영 구조:**

```
인터넷 요청
    ↓
Nginx (웹 서버)
    ├── 정적 파일 (/images, /css) → 직접 응답
    └── 동적 요청 (/api, /login) → Tomcat으로 전달
                                    ↓
                            애플리케이션 서버 (Tomcat)
                                    ↓  
                                데이터베이스
```

### 📊 웹 서버 성능 지표

**처리량 (Throughput)**

- **정적 파일**: 초당 처리 가능한 파일 요청 수
- **동시 연결**: 동시에 유지할 수 있는 TCP 연결 수
- **대역폭**: 초당 전송 가능한 데이터 크기

**지연시간 (Latency)**

- **TTFB** (Time To First Byte): 첫 번째 바이트까지 걸리는 시간
- **페이지 로드 시간**: 전체 페이지 로딩 완료까지의 시간

Nginx를 설치하자마자 별도의 셋팅을 하지 않더라도 아래와 같은 웹 사이트가 뜬다. Nginx가 아래 페이지를 띄우는 데 필요한 HTML, CSS, JS 파일들을 제공하고 있기 때문이다. 즉, 이미 Nginx가 웹 서버(Web Server)의 역할을 하고 있는 것이다.

**기본 Nginx 설정 동작:**

```
*# 기본 설정 파일 (/etc/nginx/nginx.conf)*
server {
    listen 80;                          *# 80번 포트에서 대기*
    server_name localhost;              *# localhost 도메인 처리*  
    root /usr/share/nginx/html;         *# 파일을 찾을 기본 경로*
    index index.html index.htm;         *# 기본 파일명*
    
    location / {
        try_files $uri $uri/ =404;      *# 파일 찾기 시도, 없으면 404*
    }
}
```

**실제 파일 구조:**

```
/usr/share/nginx/html/
├── index.html          ← "Welcome to nginx!" 페이지
├── 50x.html           ← 에러 페이지
└── nginx-logo.png     ← 로고 이미지
```

이처럼 Nginx는 설치 즉시 완전히 동작하는 웹 서버로서 HTTP 요청을 받아 파일을 제공할 수 있는 모든 기능을 갖추고 있습니다.
